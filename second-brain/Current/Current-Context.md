## Logo/brand-mark collaboration (2026-09-04, in progress)
Distinct from the hands-off frontend rebuild above: the user explicitly invited Claude into this one, with concrete assets, so it's not scope creep to draft from them. Given: (1) a reference image of a hexagonal stacked-plate "cube" mark — blue top plate, middle plate split green/yellow, red bottom plate, thin gaps between; (2) a Söhne (`sohne-font-family/` at repo root, "Test" trial `.otf` files — not licensed for production, fine for drafting) font import; (3) explicit instruction to keep the Google-palette colors already in `src/app/globals.css` (`--gblue`/`--ggreen`/`--gyellow`/`--gred`) and drop navy entirely from the mark.
Exploration published as an Artifact: <https://claude.ai/code/artifact/79a0d832-1a06-4234-baf7-d6eb3ec056b8> — a `Main` lockup (the literal ask: wordmark with the mark inline, light + dark backgrounds, Söhne weight tweak) plus two unsolicited bonus layout variants (icon-beside-wordmark, mark-alone/app-icon) flagged to the user as optional/skippable, not the deliverable.

Three redraws from a description of the image missed (see [[Lessons-Learned]] 2026-09-04 "measure pixels, don't redraw from memory"). The user then saved the actual reference to `referencelog.png` (repo root — now gitignored scratch file) and it was pixel-measured directly. **Confirmed mark spec**, not a guess: three identical hexagons (each 120 units wide, 71 tall — 24px point-to-shoulder taper, 21px flat-side plateau, 26px shoulder-to-point taper), stacked with a 33-unit vertical step between each hexagon's top point, drawn back-to-front as red → green/yellow (split at the vertical centerline) → blue, each with an 8-unit white stroke (`stroke-linejoin: round`) — the interlocking-notch look is pure hexagon overlap + z-order, no chevron cut or isometric cube-face split. Exact colors sampled from the reference: blue `#4285F4`, green `#34A853`, yellow `#FBBC05`, red `#EA4335` (standard Google brand hex — close to but not identical to the app's existing oklch `--gblue`/`--ggreen`/`--gyellow`/`--gred` tokens; worth a decision on which wins before this lands in code). Tried widening the stack step (33→45 units, to make the middle plate look less small relative to top/bottom) and swapping the font to **Greed** (Frost Type Foundry TRIAL, dropped at `greed-font-family/` at repo root, Standard width) in the same publish — user called the result worse and asked for a full revert of both. Reverted to the pixel-verified 33-unit-step hexagon geometry and Söhne, confirmed clean (no leftover Greed/wide-step references) before republishing. Lesson: don't bundle an unverified fix (the step change, a guess at their sizing complaint) with an unrelated confirmed request (the font swap) in one publish — if the bundle gets rejected, it's ambiguous which part failed and costs a round trip to disambiguate (see [[Lessons-Learned]]). Both `sohne-font-family/` and `greed-font-family/` are trial fonts at repo root ("Personal Use Only" license, not production-ready) — now explicitly gitignored (they were incorrectly committed earlier; untracked 2026-09-04).

**Landed in code 2026-09-04**: the reverted (33-unit-step, Söhne) version is now implemented for real in `src/components/brand/logo-mark.tsx` — `LogoMark` renders the confirmed hexagon-stack SVG inline (no more design-canvas-only mockup), and a `sohne` `next/font/local` export (bold/700 only, copied into `src/fonts/sohne/`) replaces the old system-font wordmark. Placed on the homepage (`src/app/page.tsx`) per explicit "just the logo" instruction — inline between "Kn"/"how" (the original placement), large scale, top-left, dark `#1c1917` text, matching a reference screenshot's positioning logic. Since `LogoMark`/`Logo` are shared, the sidebar and `/signup` picked up the new hexagon mark + Söhne font automatically at their existing (small, untouched) size — checked both by screenshot, both render cleanly, no layout breakage. Still open: whether the plate-size complaint needs revisiting with a different fix than the reverted one.

Two quick follow-up tweaks, same session: homepage logo size bumped (`clamp(3rem,11vw,11rem)` → `clamp(3.5rem,12.5vw,12.5rem)`), and the mark's white gap/stroke color changed from pure `#ffffff` to `#F9F8F6` everywhere in `LogoMark` (so sidebar/signup picked this up too, same as the font/shape change above).

Bug found and fixed: the blue plate's top point and red plate's bottom point rendered flat instead of pointed. Cause: the SVG's `viewBox="0 0 120 137"` bounds are exactly tangent to those two vertices, so the `stroke-linejoin="round"` join's natural outward bulge (~4 units, half the 8-unit stroke width) was being clipped by the viewport at y=0 and y=137. Fix was one line — `style={{ overflow: "visible" }}` on the `<svg>` — no coordinates, colors, or other joins touched, confirmed by zoomed screenshot against the untouched version.

Added a small "™" top-right of the wordmark on the homepage hero only (`src/app/page.tsx`, `self-start` in the flex row so it aligns to the top like the reference screenshot, not baseline; sized down to `0.16em` after a first pass at `0.28em` ran too large) — not added to the shared `Logo` component, since TM at sidebar/signup's small scale wasn't part of this ask and would be cramped there.

**Made the homepage logo draggable, and dropped the mark's gap color to `none`** (2026-09-04): the user wants to position the text and mark by dragging in the browser rather than iterating through Claude on every pixel value. `src/components/brand/draggable.tsx` is a new "use client" `Draggable` component (pointer-drag, position persisted per-id to `localStorage`, coordinate readout shown while dragging) — explicitly dev-only/ungated, flagged in its own comment to remove before shipping past prototype. The hero moved out of `src/app/page.tsx` (a server component, can't hold drag state) into a new `src/components/brand/landing-hero.tsx` client component; `page.tsx` now just does the auth check and renders `<LandingHero />`. The wordmark text and the `LogoMark` SVG are now two independent `Draggable`s (previously one inline flex lockup) — each keeps its own `em`-based sizing via a shared `LOGO_FONT_SIZE` constant so they still scale together even though they're no longer nested in the same element. Separately, `LogoMark`'s stroke color (the plate-separation halo) changed from `#F9F8F6` to `none` per explicit request — the plates now interlock with a direct color-to-color seam instead of a halo, which also applies to the sidebar/signup via the shared component. One real bug caught by `npm run lint` (not just tsc): the initial `Draggable` implementation read `localStorage` inside a `useEffect` + `setState`, which the React compiler's lint rule flags as an **error** (cascading-render anti-pattern), not just a warning — fixed by moving the read into a lazy `useState(() => ...)` initializer guarded by `typeof window`, with `suppressHydrationWarning` on the positioned element since server and first-client-render intentionally differ. Verified with a real Playwright drag + page reload, not just a screenshot.

Follow-up: the "™" was pulled out of the text `Draggable` into its own third `Draggable` (`landing-logo-tm`) so all three pieces — text, mark, ™ — move independently. Caught a real (pre-existing, now fixed) `tsc` error along the way: the lazy `useState` initializer's `JSON.parse(saved)` returned `any`, silently widening `pos`'s type and only surfacing as an implicit-`any` error on the `setPos((p) => ...)` callback once a second caller made the compiler re-check it — fixed with an explicit `useState<{x,y}>` generic and a cast on the parsed value.

**Edit-mode toggle + config export** (2026-09-04): `Draggable` now takes a `locked` prop — `LandingHero` holds an `editMode` boolean (persisted to `localStorage["draggable:editMode"]`) toggled by a bottom-right "Edit positions" / "Done editing" button; when locked, pointer handlers no-op and the cursor/touch-action revert to normal. A "Copy config" button (shown only in edit mode) reads all three `draggable:<id>` localStorage entries and both copies them as JSON to the clipboard and prints them in an on-page `<pre>` (clipboard permission isn't guaranteed, so the visible text is the reliable fallback). Important limitation surfaced here: **Claude cannot read the user's actual browser localStorage** — the user drags things in their own tab, not one Claude can inspect, so "save the current config" requires the user to click Copy config and paste the JSON back into the conversation before Claude can bake those numbers in as new static defaults. All of this verified end-to-end with Playwright (toggle on → drag → copy config → verify readout → toggle off → confirm drag no longer moves anything).

The whole editor (button included) is now further gated behind `NEXT_PUBLIC_LOGO_EDITOR_ENABLED` (`.env`, documented in `.env.example` defaulting to `"false"` there — local `.env` is currently `"true"` since the user is actively repositioning). When unset/false, `LandingHero` never renders the edit-mode button/panel and `editMode` can't become true regardless of any stale `localStorage["draggable:editMode"]`. Verified both states by screenshot (button present at `"true"`, completely absent at `"false"`, logo still renders at its positioned spot either way) before restoring to `"true"`.

**Positions committed to code** (2026-09-04): confirmed the localStorage limitation in practice — the user pushed to GitHub, opened on a different device, and got the hardcoded fallback layout instead of their dragged one, since positions never lived anywhere but their browser. Fix: the user copied their config via the "Copy config" button and pasted the JSON; those exact values are now the `initial` props in `landing-hero.tsx` (`landing-logo-text: {9.875, -10.21875}`, `landing-logo-mark: {241.3046875, -50.18359375}`, `landing-logo-tm: {696.19921875, -107.63671875}`). Verified in a brand-new Playwright browser context (no localStorage, i.e. a real stand-in for "a different device") that the layout now matches their screenshot without any drag needed. The negative y offsets don't clip against the hero's `overflow-hidden` — the font's leading/ascent absorbs it. `NEXT_PUBLIC_LOGO_EDITOR_ENABLED` stays available for further adjustments; re-copy config and re-paste here any time the positions need to move again.
