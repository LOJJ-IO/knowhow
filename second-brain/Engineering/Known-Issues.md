- **[landing / desktop]** With the Log In panel open, clicking the empty white panel outside the card band's y-range played the Get Started handoff backwards behind the panel — the landing root's click-outside handler (`isDeckKeepZone`) still ran, and the panel isn't a keep zone. - **[landing / mobile CTA]** User reported the Get Started pill "teleports left, then back" right after splitting into the two arrow circles. Not reproducible in headless Chromium (per-frame Playwright instrumentation — button-centre polling at ~15ms resolution + a CDP screencast at ~37fps — showed monotonic, jump-free separation); user confirmed it only happens on a real phone, matching the theory: the daughter circles centred themselves with `translate: calc(-50% + Npx)`, and a CSS `%` in `translate` resolves against the *element's own* box every frame — with `width` also transitioning at the same time, the browser has to resolve both from the same live layout each frame. A real mobile browser can force a synchronous reflow mid-gesture (Safari's address bar collapsing/expanding changes the viewport height it's animating against) and the two dependent interpolations can read back out of step for a frame. Headless Chromium never triggers that reflow, so it could never have shown it. Fixed by pinning the pill's un-spread width as a fixed px custom property (`--cta-box-w`, measured once via `getBoundingClientRect()`) and writing both the un-spread and spread `translate` values as literal px `calc()`s instead of `-50%` — the transition now interpolates between two fixed numbers with no live width dependency at any point. Verified geometrically identical in Chromium before/after (same start/end centres, still monotonic); not yet re-verified on the actual phone that showed it. (since 2026-09-14) — [[FEAT-landing-deck-carousel]], [[Lessons-Learned]]

## Open
- **[google / OAuth verification — launch-blocking]** Knohow's Drive permission (the full `drive` scope, used by the Drive consent flow and by the owner-owned stand-in for contractors in domainless orgs) and `admin.reports.audit.readonly` are Google **restricted** scopes. Until the OAuth consent screen passes Google's verification review (including a security assessment), they only work for accounts on the app's **test-user list** — nobody else can grant them. Review runs on Google's timeline; not submitted as of 2026-09-18. Also while the app is in "Testing" mode, **even sign-in** only works for listed test users — add collaborators under APIs & Services → OAuth consent screen → Test users. Domain-wide delegation is authorized by a Super Admin in the Admin console instead of per-user consent. See [[0004-fastapi-backend-for-auth-and-identity]], `backend/docs/gcp-setup.md`. (since 2026-09-18)
- **[backend / auth — personal OAuth callback]** Every Google flow uses one `GOOGLE_OAUTH_REDIRECT_URI` (`/auth/callback`), so Drive consent started at `/auth/personal-oauth/start` returns to `/auth/callback`, not `/auth/personal-oauth/callback`, and isn't dispatched there (purpose `personal_oauth`) — it would be treated as a login. `backend/docs/gcp-setup.md` assumes two registered URIs the code never sends. Signup was fixed the same way on 2026-09-18 ([[0008-continue-with-google-via-backend]]); personal OAuth was left alone (not asked). (since 2026-09-18)
- **[legal / privacy — launch-blocking]** The Privacy Policy (`/privacy`, [[FEAT-legal-pages]]) promises the *agreed* model from [[FEAT-drive-file-classification]], which `backend/` does not implement yet: (1) sync writes `FileIndex` rows before confirmation, but the policy says Drive metadata is kept only for confirmed company files; (2) DeepSearch can show Personal-file titles to leaders, but the policy says Personal files are never shown to the organization; (3) no discard-Personal-metadata / ID-only undecided storage / expiry exists; (4) the `personal` flag actually means Private. Do **not** connect real users to `backend/` until these are fixed or the policy is changed — publishing a privacy promise the code breaks is a legal and Google-verification risk. (since 2026-09-17)
- **[backend / invariant — FileIndex before confirmation]** The current Drive sync creates `FileIndex` entries before classification/confirmation, violating the intended invariant `¬Confirmed(Company) → ¬InFileIndex` ([[FEAT-drive-file-classification]] formal rule 3). Concretely: `reconcile_organization` (`backend/app/activity/reconciliation.py`) lists every file each member owns (`'me' in owners`) and routes each through `handle_file_created` (`backend/app/sharing/service.py`), which inserts a `FileIndex` row **with the title** — so every member's Personal files are indexed and their names retained (also breaks constraints 3 and 7). Webhook/Reports-feed creation events take the same path. Must be reconciled before the new onboarding/classification flow is considered correct. Not fixed. (since 2026-09-16)
- **[backend / invariant — Knowhow cannot assert Google ownership]** No Shared Drive support anywhere in `backend/` (no `driveId`, no `supportsAllDrives`), and the only ownership mechanism is `app/google/ownership.py::transfer_ownership` → Drive `permissions.create(transferOwnership=True)`, which Google restricts to within one Workspace domain and refuses between a consumer account and a Workspace. So any feature premised on "the company automatically owns what an outside/contractor account creates" is unimplementable as written — a Knowhow role/session does not change Drive ownership. Real options: create it as the org through Knohow (chosen for contractors 2026-09-18, [[0009-contractor-work-created-as-the-org]]), Shared Drive (org-owned at creation), or a Workspace account for that person. (Per-file transfer from a personal account isn't possible — corrected 2026-09-18.) Constrains Auto-Own. See [[FEAT-workspace-onboarding-flow]] "Three independent layers"; options written up as the open question [[0007-shared-drive-support]]. Also: `app/google/ownership.py`'s docstring calls its contents "Shared Drive ownership-transfer primitives" though nothing in it touches Shared Drives. (since 2026-09-17)
- **[backend / privacy — DeepSearch]** DeepSearch (`backend/app/search/deepsearch.py`) searches every member's entire Drive (`fullText contains`) and, for files not in `FileIndex`, shows them to any org-wide role (top_leader / authorized_user) or anyone whose visible teams include the owner's team. Nothing excludes employees' **Personal** (non-company) files, so their titles/owners can surface to leaders. Fix direction: gate results through [[FEAT-drive-file-classification]] (Company only; Personal never; unclassified excluded by default). Not fixed. (since 2026-09-16)
- **[backend / naming]** `sharing_state["personal"]`, `mark_file_personal`, `is_personal` (`backend/app/sharing/service.py`, `visibility.py`) and audit action `sharing.file_personal_designation_set` implement **Private** (company file hidden from coworkers, leaders still see it), not **Personal** (employee's own non-company file). Terms decided 2026-09-16 in [[FEAT-drive-file-classification]]. Rename to private before building classification, or Personal files would be treated as leader-visible. Not renamed yet — awaiting user go-ahead. (since 2026-09-16)

- **[landing / viewport]** Viewport sweep (375–2560 wide × 390–1440 tall, idle + open deck, Playwright) found: (1) **desktop open deck collides below ~700px tall** — `--deck-fit` bottoms out at 0.7 at 669px, so shorter windows overlap: centre card over the subhead (1280×600 −21px, 1440×600 −27px, 1920×688 −1px) and over the logo / "Features" label (1920×600 −51px); phone landscape (≥768 wide × ~390) gets the desktop layout and the card fills the whole screen. Even at 1920×780 the gaps are only 8–11px because card width caps at 68.4rem while `--deck-fit` references a fixed 956px. (2) **Wide screens lose the three-card composition** — `--deck-side-x: 73vw` grows with width but the card stops growing at 68.4rem, so the side cards drift off-screen: slivers at 1920, fully off at 2560 (at fit 1). The logo, subhead and CTAs also stop growing at ~1600px, so extra width is just empty space. (3) **Mobile Cover Flow doesn't scale with height** — card height is set by width (`min(52vw,13.5rem)` × 9/19.5 ≈ 481px), so at 375×≤688 (iPhone SE, Safari with toolbars) the card overlaps the subhead and the nav bar sits on top of it; it clears only at ~780px tall. (4) Very tall windows (1440) don't break, but the deck stops scaling at fit 1 and gaps grow to 300–500px. Awaiting the user's decisions on how each should behave. **Proposal prototyped (injected, not in source), same sweep 121 sizes:** fit the deck into the *measured* open-state gap between logo/header and subhead/footer (JS, on resize); cap desktop logo/subhead/label type by `vh` as well as `vw` (factors = the vw sizes at 1470×956, so wider-than-reference windows are unchanged); side-card spacing `max((50vw/fit + card/2)/1.5, min(73vw, card×0.981))` (identical ≤1470 wide, keeps three cards visible at 1920–3440, and a card at the 1.6-slot wrap threshold stays off-screen at any fit); mobile Cover Flow sized and centred in the measured band. Result: sizes with <8px clearance or overlap 55 → 11 (all of the 11 are 390px tall, clearing by 7px). Unchanged at 1470×956 and ≥1080 tall. Known gap in the prototype: fit recomputed on `resize` sometimes read pre-resize layout (stale fit at a few sizes) — the real version needs a ResizeObserver + rAF. Still open for the user: very tall windows (2560×1440 keeps 300–500px empty above/below). (since 2026-09-12)

Verified with a rAF hit-test recorder (who's on top where the blue card overlaps each side card, every frame): before, 12/24 scenarios bad in Chromium; after, 0/48 in Chromium and WebKit (1470×956, 1219×688; fresh, reopen after ±1/2/3/4/7 shifts, quick reopen). ## `[legal / privacy]` The Privacy Policy doesn't mention the `knohow_device` cookie (2026-09-20)
[[0011-device-remembered-accounts]] added a **long-lived browser identifier** (`knohow_device`,
1 year) holding a per-browser list of names and emails, readable **before sign-in** — the Log In
account picker. `/privacy` says nothing about it. Must be covered before launch, alongside the
existing `[legal / privacy]` blocker. Note the read endpoint is unauthenticated by necessity and
is gated only by possession of the cookie; it returns only accounts that signed in on that
browser, never an organization's membership.

## `[onboarding / linking]` A linked personal address isn't recognised at a later sign-in (2026-09-20)
`person_emails` records an address proved to belong to a person who answered "yes, I have an
organization account" ([[0013-sign-in-is-to-an-organization]]). `complete_signup` does **not** consult
it: signing in with that address again still finds no `OrgMember`, so it falls into the pending
personal-signup path and asks the same question over again. The picker shows the link (a `Personal`
chip), but nothing acts on it. Also still missing: any in-app UI to start `/auth/link-account/start`
for someone already signed in.
